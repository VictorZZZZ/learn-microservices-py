# API Docs (Redoc) — документация всех сервисов в одном месте

Единая страница документации всех микросервисов приложения:
**http://localhost:7777/docs/** — все сервисы собраны в одну спецификацию
и показаны в левой панели Redoc, сгруппированные по сервисам. Рендер —
[Redoc](https://github.com/Redocly/redoc).

Документацию отдаёт тот же nginx-контейнер, что и роутер: `nginx.conf`
и `docker-compose.yml` лежат на уровень выше, в папке gateway. Здесь —
только статика страницы.

Схема портов проекта: gateway + документация `:7777`, оркестратор `:8000`,
auth `:8001`, catalog `:8002`, profile `:8003`.

## Как это устроено

- Спецификации **не собираются** в одном месте на этапе сборки: сервисы
  отдают живые `openapi.json`, а Redoc рендерит их прямо в браузере.
  Документация всегда соответствует текущему коду, никакого build-шага.
  (Статическая сборка — Redocly CLI `build-docs` — нужна только когда
  документацию надо выложить без запущенных сервисов.)
- Спеки склеиваются в одну **прямо в браузере** (страница скачивает
  `openapi.json` сервисов и объединяет): каждый сервис становится группой
  в левой панели (`x-tagGroups`); пути получают публичный префикс gateway
  (`/catalog` + `/v1/products` = `/catalog/v1/products` — в доках сразу
  реальные URL для `:7777`); имена схем получают префикс сервиса
  (`catalog.ProductDto`) — защита от одинаковых названий в разных сервисах.
- Страница `/docs/` и спеки `/openapi/*.json` живут в одном origin
  (`:7777`) — CORS не возникает. Спеки nginx проксирует через те же
  upstream'ы, что и роутинг (см. `../nginx.conf`).
- Для каждой операции **примеры запроса генерируются автоматически**
  (curl / Python requests / JS fetch): Redoc показывает их вкладками
  (расширение `x-codeSamples`). В примерах — реальный путь через gateway,
  скелет тела из required-полей схемы и заголовок `Authorization`, если
  операция защищённая. Автопримеры на десятках языков «из коробки» умеют
  только Scalar / коммерческий Redocly API Reference — vanilla Redoc
  показывает только то, что лежит в спеке, поэтому генерируем сами.
- `redoc.standalone.js` лежит в репозитории (`site/`), а не подключается
  с CDN — контейнер работает без интернета и без внешних зависимостей.

Состав папки:

```
gateway/api-docs/
└── site/
    ├── index.html       # страница: склейка спек в одну + рендер Redoc
    └── redoc.standalone.js
```

## Запуск

Нужен запущенный Docker Desktop и поднятые сервисы (иначе их спеки не
загрузятся — Redoc покажет сообщение об ошибке):

```bash
cd auth-service     && uvicorn app.main:app --reload --port 8001
cd catalog-service  && uvicorn app.main:app --reload --port 8002
cd profile-service  && uvicorn app.main:app --reload --port 8003
```

Контейнер gateway (роутер и документация — один контейнер):

```bash
cd gateway
docker compose up -d
open http://localhost:7777/docs/
```

## Добавить новый сервис (например, оркестратор)

1. В `../nginx.conf` — раскомментировать (или добавить) `location =
   /openapi/orchestrator.json { proxy_pass ...; }`.
2. В `site/index.html` — раскомментировать запись в списке `APIS`
   (ключ, имя, префикс gateway, путь к спеке).
3. `docker exec gateway nginx -s reload` — контейнер пересоздавать не нужно.

## Ограничения

- Redoc — read-only, кнопки «Try it out» в нём нет (осознанный дизайн
  инструмента). Выполнять запросы — curl'ом через gateway
  (`http://localhost:7777/...`, примеры в gateway/README.md) или через
  Swagger UI отдельного сервиса напрямую на его порту
  (`http://localhost:8001/docs`).
- Если сервис не запущен, его вкладка покажет ошибку загрузки спеки —
  остальные сервисы при этом доступны.
